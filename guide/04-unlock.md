# 04 — Разблокировка загрузчика

Перед этим шагом ОБЯЗАТЕЛЬНО выполнен гайд 03 (есть `chkcode_backup.bin`).

## Как это работает (одним абзацем)

В загрузчике (ABL) этой модели есть сервисная проверка `KcFastbootCheck()`:
если в начале раздела `chkcode` лежат 8 байт `LOOT`+`BFCK`, ABL считает
устройство сервисным: регистрирует ВСЕ fastboot-команды и пропускает
проверки блокировки внутри `flash`/`erase`, а команда `flashing unlock`
перестаёт требовать разрешение OEM. Само состояние «unlocked» при
подтверждении на экране записывается через TrustZone в devinfo.
Побочный эффект: с магией телефон грузится ТОЛЬКО в fastboot —
Android не стартует, пока магия не снята (гайд 05).

## 4.1 Запись магии (телефон в Android, диаг-композиция активна)

```bash
cd tools
python3 backup_chkcode.py -o chkcode_backup.bin     # если ещё не сделано
python3 kdiag_shell.py "setprop vendor.kc.diag.status start"   # демоны kc_diag
python3 unlock_chkcode.py --backup chkcode_backup.bin
```

Если `kdiag_shell.py` вернул `DIAG_BAD_CMD` и класс не поднялся — у вас
пустой раздел `sysprop` (розничная норма): init-триггер класса kc_diag
требует `vendor.kc.diag.fact=kcfactoff`, которую некому выставить.
Используйте запуск демона напрямую, это работает на любом юните:

```bash
python3 cve31317.py --cmd "setprop ctl.start fs_sys_call_diag ;" \
    --check-prop init.svc.fs_sys_call_diag=running
```

Полная процедура для этого случая (с диагностикой каждого шага) —
гайд 06; дальше шаги записи/анлока идентичны.

Скрипт спросит подтверждение, запишет 8 байт, прочитает назад и
проверит. В случае «ОШИБКА: магия не подтвердилась» — НЕ перезагружайте
телефон, восстановите бэкап (гайд 05, раздел 5.3) и разберитесь,
почему запись не прошла (обычно — не запущен класс kc_diag).

## 4.2 Разблокировка

```bash
adb reboot bootloader
fastboot devices                       # должно показать серийник
fastboot flashing unlock
```

На экране телефона появится запрос подтверждения —
**выберите «разблокировать» кнопками громкости** (Vol Up = подтвердить).
Процедура затрёт данные (data) — так задумано; внешней карты нет.

Проверка:

```bash
fastboot oem device-info | grep -i unlocked     # Linux
fastboot oem device-info | findstr /i unlocked  # Windows
# (bootloader) Device unlocked: true
```

## 4.3 Чего НЕ делать в разблокированном fastboot (выстраданный список)

**Общее правило.** После разблокировки вам доступны все команды fastboot
(`flash`, `erase`, `boot` и другие). Их выполнение — прямо или косвенно —
может привести к кирпичу, **из которого может не быть выхода**: модель снята
с производства, сервисных инструментов в открытом доступе нет, кнопочных
входов в fastboot/recovery на user-прошивках нет, EDL требует подписанного
programmer-файла, которого нет в публичном доступе. Ниже — конкретные
известные грабли, но список не исчерпывающий: думайте перед каждой командой,
которая что-то меняет.

- ⛔ **НЕ прерывать** `fastboot flash ...` на разделах внутри `super`
  (system/vendor/product/system_ext/odm). Прерванная прошивка оставляет
  COW-разметку Virtual A/B в повреждённом состоянии — исправляется
  только через fastbootd (`reboot fastboot` → `delete-logical-partition
  <name>-cow`), которого с ними же можно и не иметь.
- ⛔ **НЕ выполнять** `fastboot -w`, `fastboot erase userdata`,
  `fastboot erase metadata`: у этой модели recovery/format в некоторых
  контекстах не может переформатировать metadata («Permission denied»
  в mke2fs) — лечится только прошивкой готовых файловых образов,
  для чего нужен fastboot, который в момент ошибки как раз недоступен.
- ⛔ НЕ прошивать GPT и boot-цепочку из чужих пакетов.
- ⛔ **`fastboot boot <кастомный-образ>` — без необходимости НЕ использовать.**
  Проверенных образов для этой модели нет (грузить нечего), а цена ошибки
  высока. Если всё же пробуете свой образ, обязательны три условия:
  1) заголовок образа — строго **v2** (v2-поля @1648 заполнены): при
     header_version 0/1 ABL не вычисляет DtbOffset/ImageSize и молча
     остаётся на лого после OKAY — ядро не запустится вовсе; v3 непригоден:
     ABL дотянет стоковый vendor_boot с флеша и подмешает чужой init;
  2) ramdisk-тест обязан **самозавершаться**: сторожевой reboot
     ("bootloader") через N секунд в любой ветке, включая зависшие;
     `panic=N` в cmdline — НЕ замена (паника = грязный резет);
  3) в kernel.config проверено, **кто кормит watchdog** (либо
     CONFIG_WATCHDOG + узел qcom,wdog, либо п.2) — иначе PMIC-watchdog
     зарежет устройство через ~10 секунд зависания.
- ⛔ **Считать slot-retry-бюджет при сериях `fastboot boot`**: каждый
  «грязный» резет (паника/watchdog) до userspace декрементирует
  slot-retry-count активного слота; при исчерпании ABL пометит его
  unbootable и переключит на второй слот — где на обновлявшихся OTA
  устройствах лежит старая цепочка (несовместимый микс → вечный цикл
  без входов: кнопочные переходы закрыты, USB-host для FASTBOOT-флешки
  не поднимается). До/после серии проверяйте `fastboot getvar
  slot-retry-count:a/b`; при исчерпании — `set_active <слот>` до
  продолжения.
- ✅ Гипотетически безопасно: `getvar`, `oem device-info`, `flashing
  get_unlock_ability`, прошивка отдельного раздела ЗАВЕРШЁННЫМ до конца
  образом, для которого у вас есть оригинал (бэкап или OTA).

## 4.4 После анлока

Телефон в цикле fastboot (это магия, не поломка). Сначала гайд 05 —
возврат нормальной загрузки. Дампы разделов теперь возможны из
fastbootd/bootloader-независимых сред, но выходят за рамки этого
репозитория; здесь анлок — конечная цель.
